兼容性矩阵

按真实能力标注 · 不写「全兼容」

同一个插件能不能装，取决于两件事：它跑在哪个宿主里、它要不要调用协议端动作。 本市场的插件是零依赖 .mjs，跑在市场自己的 MCP 进程里，所以只对 DSH 宿主有效； 纯本地工具（报时、抽签）不碰协议端，官方通道也能用；要发消息、禁言的则必须 OneBot v11。 标了 主链路 的那一行（SnowLuma + qq-bridge + DSH）是它们的主场， 其余列说明的是「这个框架的原生插件能不能装进这个框架」，不是「本市场插件到处都能跑」。 AstrBot / Koishi / NoneBot / Yunzai 的原生插件只在各自框架内可用，跨框架现在是 不支持，矩阵里就这么写。

插件从哪来、能不能用

这里不玩虚的——来源和实测结果都摊开给你看。

目录
50 个插件、84 个工具的定义

名称、功能描述、工具名与参数，抓取自公开的 QQ 插件市场站点，并保留了各插件的上游出处（AstrBot / NoneBot / Koishi / Yunzai 社区同名插件），卡片上的「源自 xxx」就是那个链接。

实现
每个插件都是可运行的代码

原站的插件依赖它自己的加载器，抓不到实现。所以 50 个插件的能力都由本项目重新写成零依赖的 MCP 工具，跑在 Node 上，不装任何第三方包。

实测
64 项当场跑通，0 项报错

仓库自带 node scripts/verify-plugins.mjs，用真实参数把 84 个工具全跑一遍（现在默认就在沙箱里跑）：64 项直接通过；16 项因为本机没开 QQ 显示「需在线」（群管理 8、群信息 3、空间动态 4、表情包发送 1）、4 项因为没填接口 Key 显示「需配置」（语音 1 项、识图 2 项、认视频 1 项）——都是环境问题，不是插件坏了。免费画图接口偶尔限流，那一项会被标成「需公网」而不是算失败，所以通过数会是 63 或 64。你可以自己跑一遍复核。

隔离
插件跑在沙箱里，不是跟你一个进程

每个插件调用都在独立子进程里执行，用 Node 的权限模型压住能力：插件代码写不了任何文件、起不了子进程、读不到 config.json 里的密钥，这些由系统直接拒绝（ERR_ACCESS_DENIED），不是「代码里说好了不许」。要发消息、要存自己的数据，全部回到主进程按插件 id 校验后执行。实测拦截图见 docs/SANDBOX.md。

边界
哪些事它做不了

不抓版权音视频（点歌只给平台搜索链接）；群里禁言/踢人受机器人自身群权限限制；联网插件依赖公开免费接口，断网时会给出明确提示而不是假装成功。沙箱拦的是写盘/起进程这类越权，拦不住插件联网（Node 的权限模型目前不管网络），也没有做 CPU/内存配额。

🔌 接入 DSH（DeepSeek Harness）

与 qq-bridge 官方挂 mcp__snowluma__ 使用同一份配置文件、同一格式，互不冲突；不改动 qq-bridge 任何文件。

1
确认链路通SnowLuma（3000/3001）与 qq-bridge 已按教程跑通，DSH 里发一句话有回复。
2
一键写入点下面的「一键接入 DSH」，把本市场写进 cordis.patch.yml（自动备份、可重复执行）。
3
完整重启 DSHpreset 与 MCP 只在启动时加载，务必完整退出再打开。
4
验证生效在 DSH 里搜 mcp__qqbot__，能看到工具即搭桥成功。
